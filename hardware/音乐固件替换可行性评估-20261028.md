# 把小智 app1 换成 xiaozhi-esp32-music 音乐固件的可行性评估

- 评估时间：2026-10-28（Asia/Shanghai）
- 设备：ESP32-S3 N16R8，16 MiB Flash，当前双应用布局
- 被评估对象：<https://github.com/Maggotxy/xiaozhi-esp32-music>（小智开源音乐固件，MIT，基于 `78/xiaozhi-esp32`）
- 结论口径：本机实测 + 源码核对 + 公开社区材料；未上板刷写该固件，涉及"实板听感/触摸/联网"的结论明确标注未验证

## 0. 结论

**技术上存在可行路径，但不建议按原样直接替换现有 app1。**

**补充实测（2026-10-28 21:30）**：已用恢复的 IDF 5.4.3 成功编译 fork 的参考板（esp-box-3），产物 `xiaozhi.bin` = **4,078,576 B（3.89 MiB）**，唤醒模型 `srmodels.bin` 另有 291,042 B。**现有 3 MiB app1 放不下，直接替换必须先重分区**（历史 7.5/5.0 布局可容纳，见 §5）；这也证实先前"1.4–2.0 MB"的估算偏低。

三条决定性理由：

1. **点歌依赖一台已经不可用的私有服务器。** 固件把点歌地址硬编码为 `http://110.42.59.54:2233/stream_pcm`，没有配置项、没有 HTTPS、没有备用源，也没有本地曲库或 SD 卡回退。2026-10-28 实测：主机能 ping 通，但 2233/80/443 端口全部拒绝连接；外部 4 个探测节点 3 个拒绝、1 个超时。仓库 issue #15（2026-03-27 提交、至今 open、0 回复）标题就是「连不上服务器，无法播放音乐」；该地址是 2025-11-21 才从旧域名 `www.xiaozhishop.xyz:5005` 迁移过来的，B 站 2026-10-18 的复刻反馈也明确说"程序里写死的音乐接口不能用了"。**现在刷入，音乐功能等于零；要能点歌必须先自建服务器（0.5~1 人日 + 自有音源/版权）。**
2. **基线落后 6 个 minor 版本，与本地定制完全不兼容。** fork 的 `PROJECT_VER` 是 `1.8.5-m2`（基线经文件级指纹确认是上游 **v1.8.5**，2025-08-01），而本项目的 app1 是官方 **v2.5.0** + 依依板型/双应用补丁。两者在 IDF（5.4 vs 6.0.1）、LVGL（9.2.2 vs 9.5.0）、`Application`/`Display`/`AudioService` 架构上都是代差；fork 的改动恰好全部落在这些被重构过的文件上（详见 `build/eval/fork-analysis.md` §2、§3）。
3. **双应用契约必须整套重做。** 现有 app1 与桌面之间有：NVS Wi-Fi/UUID 导入、`ExitToDesktop()` 切回 app0、桌面 `xiaozhi_voice.cpp` 的 `project_name=="xiaozhi"` 与版本前缀校验、音量/亮度同步、USB 串口诊断（`status` JSON / `tap` / `screenshot`）。fork 一样都没有；缺了退出桥接，从桌面切进去后**可能回不到桌面**；OTA 又仍指向官方 `api.tenclass.net`，一旦触发更新会写进 **app0（桌面）**。

如果目标是"让依依能听歌"，优先做的是**先确认音乐来源**，而不是换固件。见 §6。

## 2. 音乐是怎么实现的（以及它依赖什么）

点歌链路（`main/mcp_server.cc:110-160`、`main/boards/common/esp32_music.cc`）：

1. 云端 LLM 调用设备 MCP 工具 `self.music.play_song(song_name, artist_name)`；
2. 设备请求 `http://110.42.59.54:2233/stream_pcm?song=…&artist=…`，返回 JSON 的 `audio_url` / `lyric_url`；
3. 流式下载 MP3 → libhelix 解码 → 双声道混单声道 → `Application::AddAudioData()` 直接写 codec 输出（**绕过 audio_service，不重采样**，只把 I2S 时钟切到 44.1 kHz；仅在设备 idle 时出声，状态一变即停播且不续播）；
4. 歌词（LRC）从服务器下载，逐句通过 `display->SetChatMessage("lyric", …)` 显示；频谱是 `lcd_display.cc` 里 512 点 FFT + LVGL canvas 绘制。

关键事实：

- 无备用源、无配置项；服务器地址写死在源码里。
- 明文 HTTP；鉴权是写死的静态密钥 `your-esp32-secret-key-2024` + MAC/ChipID/时间戳，会向第三方上报设备 MAC。
- 服务端未开源，仓库没有 `server/` 目录；作者只在 README 写"音乐服务器提供者（为爱发电）：cz"。
- `Download()` 在启动播放线程后就返回 true，即使后续 `audio_url` 404，工具也可能先回"音乐开始播放"。
- README 还要求在 `xiaozhi.me` 后台把角色改成 DeepSeekV3 并在人物介绍里写"只用 `self.music.play_song`，禁止 `search_music`"——这会改变设备平时对话的工具选择；官方云端本来有 `search_music`（少量歌曲）能力。

| 桌面识别 | `xiaozhi_voice.cpp:15-21` 只认 `project_name=="xiaozhi"` 且版本以 `2.1.0`/`2.5.0` 开头；fork 版本是 `1.8.5-m2`，需改桌面或改 fork 版本号 | 0.1 人日 |
| 分区/体积 | 见 §5：fork 参考板实测 **4,078,576 B**，3 MiB app1 放不下，**必须**从 9.5/3 重分区（推荐恢复历史 7.5/5.0），并改两份 `partitions.csv`、`upload.maximum_size`、烧录脚本后整片重刷 | 0.75 人日 + 验证 |
| 资源分区 | fork 资源模型是 0xF0000（960 KiB）世代，与本项目 2.5 MiB/2.5.0 资源不同；需烧 fork 的 `generated_assets.bin`，且 fork 用 `model` 分区名（本板叫 `assets`），需对齐 label | 0.2 人日 |
| OTA / 资源自动更新 | 必须关闭 `CheckNewVersion` / `CheckAssetsVersion`，否则可能被官方固件覆盖（且 OTA 会写到 app0 = 桌面）。本地 2.5.0 已在 `ota.cc` 里强制"无新版本"，移植这条补丁即可（约 10 行） | 0.2 人日 |

| 语音基线回退 | 1.8.5 的语音栈（esp-sr 2.1.4、协议、状态机）比 2.5.0 旧 10 个月；`xiaozhi.me` 兼容性需实测 | 实板验证 |

## 5. Flash 空间核算（已实测：必须重分区）

实测（2026-10-28 构建产物）：

| 分区 | 容量 | 已用 | 余量 |
| --- | --- | --- | --- |
| app0 桌面（0x980000） | 9,961,472 B | 5,787,392 B（今天 19:51 构建，字体优化后） | 4.17 MB |
| app1 小智（0x300000） | 3,145,728 B | 2,722,064 B（官方 2.5.0） | 423,664 B |
| assets（0x280000） | 2,621,440 B | 1,664,265 B | 957,175 B |
| spiffs（0xF0000） | 983,040 B | 桌面数据 | — |

**fork 实测体积（IDF 5.4.3，参考板 esp-box-3）：**

| 产物 | 字节 | 说明 |
| --- | ---: | --- |
| `xiaozhi.bin` | **4,078,576**（3.89 MiB） | 参考板；依依板移植后预计 4.0–4.2 MB |
| `srmodels.bin` | 291,042 | 唤醒词模型，独立分区（fork 默认放 `model` 0x10000 0x F0000） |

结论与方案：

- **3 MiB 的 app1 装不下 4.08 MB，直接替换必须重分区。** 桌面现在只有 5.79 MB，缩 app0 很安全。
- 可选布局（app1 偏移随 app0 大小变化；两份 `partitions.csv`、`upload.maximum_size`、烧录脚本都要同步改）：

| 方案 | app0 | app1 | assets | spiffs | app0 余量（对 5.79 MB 桌面） | app1 余量（对 4.08 MB fork） |
| --- | --- | --- | --- | --- | --- | --- |
| 现状 | 0x980000 (9.5 MiB) | 0x300000 (3 MiB) | 0x280000 | 0xF0000 | 4.17 MB | **-0.93 MB（放不下）** |
| 方案 1（推荐，历史验证过） | 0x780000 (7.5 MiB) | 0x500000 (5.0 MiB)，偏移改 0x790000 | 0x280000 | 0xF0000 | 1.98 MB | 0.94 MB |
| 方案 2 | 0x800000 (8.0 MiB) | 0x480000 (4.5 MiB)，偏移改 0x810000 | 0x280000 | 0xF0000 | 2.48 MB | 0.44 MB |
| 方案 3 | 0x900000 (9.0 MiB) | 0x380000 (3.5 MiB)，偏移改 0x910000 | 0x280000 | 0xF0000 | 3.17 MB | **-0.6 MB（仍不够）** |

- 分区/标签：fork 需要 `model` 分区存放 `srmodels.bin`（291 KB），本板 assets 分区 2.5 MB 绰绰有余；但本板当前 label 叫 `assets`（官方 2.5.0 用），移植时要改名或按 fork 的 srmodels 分区配置对齐，回滚时再换回。
- 注意：应用 bin 不内嵌分区表（运行时按 label/type 查找），改分区表后官方 app1 镜像不必重编即可回滚；但桌面 Arduino 构建使用 sketch 内 `partitions.csv`，改表后必须重编桌面。另外本机 **IDF 6.0.1 工具链已被删除**（与 5.4.3 一起丢失、目前恢复了 5.4.3），若将来需要重编官方 app1，要先重新下载约 1.8 GB 的 IDF 6.0.1；现有 `build/official-xiaozhi/` 产物足以回滚，不依赖重编。
- 重分区需要同步改 `hardware/arduino/yiyi_desk/partitions.csv`、`hardware/esp-idf/yiyi_xiaozhi/partitions/yiyi.csv`、`build.ps1` 的 `upload.maximum_size`、`flash_dual_app.ps1` 的容量校验，并重刷分区表 + 两个应用 + 资源。
- NVS（0x5000 = 20 KiB）目前余量有限，fork 的 `Settings`/SsidManager 若新增键需核算；这是移植时容易忽略的小坑。

## 6. 路线对比与建议

| 路线 | 做法 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 直接替换 app1 为 fork | 板型移植 + 桥接 + 关 OTA + 重分区（必需）+ 自建服务器 | 9–15 人日 | 极高（服务已死、停更、旧基线、功能倒退） | 不推荐（除非只想一次性体验） |
| B. 把音乐模块移植进官方 2.5.0 | 把 3 个新文件 + 10 处修改适配到 2.5.0（Display/AudioService/MCP）+ 自建 API/自有曲库；音频走 AudioService PCM 注入 + `esp_ae_rate_cvt` 重采样到 16 kHz，避免直写 codec 的并发/采样率/省电坑 | 5.5–9.5 人日 | 中（保住现有板级/双应用/诊断，风险集中在音频注入与 320×240 频谱适配） | **若确定要"长期可维护的点歌"，这是 fork-analysis 推荐路线** |
| C. 桌面 app0 内置播放器 | 桌面已有 Wi-Fi/ES8311/LVGL，加 MP3 解码 + 播放 UI；不换小智 | 3–5 人日（估） | 中（要自己解决音源与 44.1 kHz 输出） | 如果音乐由触摸/预设歌单控制，这是最可控的"礼物向"方案 |
| D. 不改固件，用官方云端音乐 | 先用现设备验证"小智，放一首歌"；官方云端有 `search_music`（曲库少） | 0 | 低（曲库/可用性待实测） | **先做这个验证** |
| E. 自建 xinnan 服务端 + `play_music` | 整机服务端迁到自建，预置本地歌单，走 TTS 音频队列 | 1–2 天 + 运维 | 中（要接受自建服务器） | 固定几首歌的备选 |

**推荐顺序：**

1. **先零成本验证 D**：在现有设备上直接说"小智，播放一首歌 / 播放《晴天》"，确认官方云端 `search_music` 当前是否可用、曲库够不够。如果够用，换固件就完全没必要。
2. 若不够，再和"音乐来源"一起决策：
   - 能接受固定歌单/自建服务 → E（不动固件最稳），或 C（桌面播放器，礼物感更强）。
   - 坚持"任意点歌 + 语音控制" → B；但先确认音源与版权，且接受自建 API 的运维。
   - 只有想体验这个固件本身，才走 A，并把它当一次性实验：完整备份 → 只写 app1+assets → 实板验证（语音/点歌/退出/OTA 已关）→ 失败可回滚。

## 7. 若要继续（最小验证方案）

前提：用户确认要投入，且音乐源可解决（自建 `/stream_pcm` 兼容服务或等作者更新服务器）。

1. 完整 Flash 备份（16 MiB 全片），并保留 `build/official-xiaozhi/{xiaozhi.bin,generated_assets.bin,partition-table.bin}` 作为回滚镜像（当前版本已在 `hardware/全部固件烧录验证.md` 记录哈希）。
2. 工具链：本项目原有的 `.cache/yiyi-xiaozhi`（IDF 6.0.1 与 5.4.3 两套源码）已被删除；本次评估已重新下载并恢复 **IDF 5.4.3** 到 `C:\Users\Tian\.cache\yiyi-xiaozhi\esp-idf-v5.4.3`（Python env `idf5.4_py3.13_env` 与 xtensa 工具链沿用），fork 的 46 个组件已下载到 `music-fork-build/managed_components`。IDF 6.0.1 若要重编官方 app1，需另外下载约 1.8 GB（现有官方 bin/assets 可直接回滚，不必重编）。
3. 在 fork 中新增 `yiyi-es3c28p` 板型（ILCD 驱动/触摸/ES8311/退出按钮/诊断），加 `desktop_bridge`，把 `WifiBoard` 改成"不启动 AP 配网"，关闭 OTA 与资源版本检查，设置 `PROJECT_VER="2.5.0-music"` 或放宽桌面版本校验。
4. 分区：fork 参考板实测 4.08 MB，当前 3 MiB 放不下；按 §5 方案 1 恢复 **7.5 MiB / 5.0 MiB** 布局（本板跑过）。先改两份 `partitions.csv`、`upload.maximum_size`、`flash_dual_app.ps1` 容量校验，再构建并整片重刷分区表 + 桌面 + app1 + `srmodels.bin`。
5. 只写 app1 + 模型分区验证：语音唤醒/对话、点歌（自建服务）、歌词/频谱、退出按钮回桌面、重启回桌面、Wi-Fi 断开恢复。
6. 任一环节失败：按备份恢复分区表/app0/app1/assets，或只回写官方 app1+assets（桌面不动）。

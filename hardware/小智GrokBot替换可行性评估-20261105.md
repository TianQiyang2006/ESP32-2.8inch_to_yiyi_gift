# 小智 GrokBot 替换可行性评估 · 2026-11-05

结论：**可以移植到依依的 ES3C28P；原分支没有该板型，不能把 StopWatch 的整包固件直接写入当前设备。** 源码和资源体积已检查，尚未完成 ES3C28P 目标固件编译与实机验证。本轮没有改动生产固件源码、分区表、设备或 VPS。

## 检查对象与功能

- 仓库：[Ocean-lhy/xiaozhi-esp32，dev-grokbot](https://github.com/Ocean-lhy/xiaozhi-esp32/tree/dev-grokbot)。检查前后分支 HEAD 均为 `1e1df1d94bd4a984f899e80b951552f93da5d6ae`。
- 下载源码的 `CMakeLists.txt` 版本为 `2.5.3`，最低 ESP-IDF `6.0.1`，推荐 `release/v6.1`。
- GrokBot 是动态表情界面：保留小智语音/协议，将聆听、思考、说话、通知和情绪映射到 28 组灰度动画。此分支没有新增直接连接 xAI/Grok 模型的客户端配置，默认后端仍是小智。
- GrokBot 只在 `m5stack/stopwatch-grokbot` 板型中接入。M5Stack 使用 CO5300 466×466 QSPI 80 MHz、不同的音频引脚与电源管理器；本机为 ILI9341 320×240 SPI 20 MHz、FT6336G 与 ES8311，不能沿用其板级初始化。
- 工程已有 ILI9341 和 ES8311 驱动；本地原官方 `hardware/esp-idf/yiyi_xiaozhi/main/boards/yiyi-es3c28p/` 的 IDF 6 板型可作为移植参考，24 kHz 音频及电池规则应以当前运行的 `yiyi_music` 适配为准。

## 实际资源打包

当前 `app1` 为 5 MiB，`model` 为 2.5 MiB；桌面 `app0` 为 7.5 MiB，LittleFS 位于 `0xf10000`。新分支运行时通过 `assets` 标签读取资源，当前 `model` 标签及内容格式需要相应迁移。

原始动画包为 **3,961,667 B**，仅动画就超过 2.5 MiB。使用该分支自带 `scripts/build_grokbot_subset.py` 对全部 28 组动画缩放，再使用其 `pack_assets_simple()` 将动画、中文字体、模型、索引与包头一起打包，结果如下：

| 动画 | 中文字体 | 完整资源包字节 | 距现有 2.5 MiB 容量 | 判断 |
| --- | --- | ---: | ---: | --- |
| 360×360 原始 | 20px / 4bpp | 5,540,659 | 超出 2,919,219 | 放不下 |
| 240×240 | 14px / 1bpp | 3,003,026 | 超出 381,586 | 放不下 |
| **200×200** | **14px / 1bpp** | **2,432,238** | **剩余 189,202（184.8 KiB）** | **可作为保留分区容量方案** |
| 200×200 | 16px / 4bpp | 3,048,606 | 超出 427,166 | 需要增大资源区 |
| 200×200 | 20px / 4bpp | 3,450,118 | 超出 828,678 | 需要增大资源区 |
| 160×160 | 14px / 1bpp | 2,004,340 | 剩余 617,100 | 更宽裕，动画更小 |
| 160×160 | 16px / 4bpp | 2,620,708 | 剩余 732 | 余量过小，不采用 |

这些是体积验证样包，不能作为发布镜像烧录：模型采用本地原官方 2.5.0 资源内的 291,042 B 模型，20px 字体也取自该归档；14px、16px 字体从 `78/xiaozhi-fonts/main/cbin` 下载。实际移植须由固定版本的 IDF/组件重新生成资源，并再次校验体积、模型兼容及汉字显示。

现有 app1 镜像 4,106,608 B 及其剩余约 1.08 MiB **不能用来推算新分支镜像大小**。新分支尚未对本板编译；5 MiB 应用区能否容纳最终程序，需要构建产物验证。默认上游 16 MiB 分区表给 assets 8 MiB，并使用不同的 NVS/OTA/应用偏移，不适用于当前桌面共存布局。

若要求较大的 16px 字体，可在最终应用镜像足够小时，考虑保持 app0 与 LittleFS 不动，将 app1 改为 4.5 MiB、assets 改为 3 MiB。该方案为候选，需按编译结果决定，并备份后同步分区表及安装/回滚脚本。本轮不改分区。

## 移植必须覆盖的项目

1. **新建独立板型**：复用已验收的 ILI9341 初始化、屏幕旋转/颜色、FT6336G 坐标校准、ES8311 引脚和低电平功放使能，接通 config.json、Kconfig 和 CMake 选板链。
2. **横屏布局**：GrokBot 显示类目前硬编码圆屏的顶部 56px、底部 66px 留白；需要为 320×240 重新安排状态、动画、字幕及退出按钮。TE 信号参数允许 `GPIO_NUM_NC`，本板使用无 TE 模式，不沿用 StopWatch 的 TE GPIO。
3. **桌面桥接**：保留桌面 Wi-Fi、UUID、亮度、音量及触摸校准的 NVS 契约；提供退出回 app0 和 `voiceReturn` 标记；保证离线或服务连接失败时仍能返回。
4. **入口版本识别**：桌面 `src/xiaozhi_voice.cpp` 只接受 `2.1.0` 或 `2.5.0` 前缀。上游 `2.5.3` 会被判断为未安装，需要增加明确受支持的新版本。
5. **OTA 与资源更新**：上游 `Ota::Upgrade()` 使用 `esp_ota_get_next_update_partition()`，运行于 app1 时会选择桌面 app0。自动升级及 MCP 固件升级入口必须统一限制。资源下载也需要防止普通资源包替换掉 GrokBot 动画。版本发现、激活和协议配置应保留。
6. **语音、电池与诊断**：保持已修复的 24 kHz 语音输出及正确上行重采样、当前半双工行为、电池电压曲线/提示规则及 USB 串口诊断。M5Stack 的充电芯片代码不适用于本板。
7. **功能差异**：新分支没有当前 fork 的 `self.music.play_song`、`self.music.control`、歌词/频谱等音乐接口，app1 语音点歌需另行移植。桌面 app0 的独立音乐 App 属于另一套实现，替换 app1 本身不会更新它，但切换回归仍需验证。VPS 的现有点歌与提醒工具须逐项确认调用契约，不能只因都支持 MCP 就视为完全兼容。

## 性能与验证边界

200×200 RGB565 每帧 80,000 B，30 FPS 需 2.4 MB/s；现有 20 MHz 单线 SPI 理论上限 2.5 MB/s，尚未计入命令、LVGL、解码及调度开销。建议先以约 20 FPS 为目标，验证帧时间和语音连续性，再决定是否提高刷新率。160×160 在 30 FPS 时为 1.536 MB/s，可作为画面速度优先的备选。

200×200 动画的双 RGB565 帧缓冲及 packed/delta 缓冲合计约 200,000 B，适合放 PSRAM；本板有 8 MiB PSRAM，但音频所需内部 RAM、DMA、任务栈和实际剩余量仍需目标构建及运行测量。

已经完成：

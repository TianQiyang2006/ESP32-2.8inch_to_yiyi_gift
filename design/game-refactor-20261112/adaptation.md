# 四款游戏替换方案：硬件适配审查

日期：2026-11-12。适用范围：ESP32-S3、320×240横屏、FT6336G触摸、Arduino ESP32 2.0.17、LVGL8.4。此文件是设计确认阶段的源码与既有构建证据审查；没有打开串口、构建新固件或刷写设备。当前可操作网页与原生LVGL截图分别验证规则交互及小屏绘制，不能据此报告实物帧率、触摸手感或声音通过。

## 替换范围与入口

用户要求“全部替换”，本方案据此把原游戏厅15款以及独立俄罗斯方块一起替换为四款：小黑快跑、拼块逃脱、切水果、猜色密码。最终桌面保留一个“游戏厅”入口，厅内四卡两行排列。

现有入口在`hardware/arduino/yiyi_desk/src/gift_ui.cpp:438`：六个第二页应用含俄罗斯方块及游戏厅；动作绑定在945、948行，构建和刷新调用在1040、1063行。正式实施需同时调整卡片排列、事件、cleanup、back/canBack、build/refresh，不能仅遮掉旧图标后留下旧模块或资源。

`src/app_state.h:25`定义的App数值也用于导航与状态输出；`src/nav_logic.h:28`明确保留数值稳定，`NavAppCount=19`。建议保留旧Tetris数值为退役占位，关闭其桌面入口及旧渲染调用；旧串口`app tetris`如保留兼容，应明确转到统一游戏厅。不要通过删除枚举中项而无意改变Music、Timer、Arcade的编号。新的四个游戏ID仅在游戏厅内部定义，不复用旧15项成绩数组位置。

## 输入链路的真实约束

1. `src/touch.cpp:59`每次以I²C读取触点；`begin():160`为400kHz，超时10ms，保留既有仿射校准与单指映射。当前没有多点手势API，不设计双指缩放或同时按键。
2. `lv_conf.h`未覆盖`LV_INDEV_DEF_READ_PERIOD`。实际库`C:/Users/Tian/Documents/Arduino/libraries/lvgl/src/lv_conf_internal.h:228`默认30ms。刷新也默认30ms（同文件219行）；`lv_conf.h:17`记录过往16ms刷新未带来效果而保留默认值。不要把现有游戏25ms规则timer误认为30ms以下的输入采样保证。
3. `touch.cpp:119`要求连续两次释放才报告松手，通常会多等一个读取周期。跑酷用按下即触发，切水果在`LV_EVENT_PRESSING`期间连续处理；点提交/菜单才使用普通CLICKED。
4. `desk.cpp:305`的全局手势在松手后判断，水平位移阈值约45px；这条路径适合翻页，不能承担果切或拖块。游戏采用自身的PRESSED/PRESSING/RELEASED/PRESS_LOST，类似现有`arcade_action.cpp:163`的拖动实现，并使用`LV_OBJ_FLAG_PRESS_LOCK`保证拖出原控件仍可收尾。
5. `desk.cpp:314`已经让Arcade独占包括左边缘在内的滑动。新游戏沿用这一边界，松手后不再把同一笔操作作为一次方向命令重放。全局手势的`wait_release`只清理最终点击，不应撤销已经完成的线段或拖动。
6. 在实际帧间隔较大时，采用相对游戏时钟和有限补步；不要在恢复后一次追赶数秒。旧实现`arcade_action.cpp:269`已有暂停后抑制追赶的模式可复用。

## 渲染、内存和容量预算

`src/display.cpp:201`已为显示分配a、b、frame三张必需RGB565全屏缓冲，并为切页快照分配一张可选outgoing。每张320×240×2=153,600 B，正常合计614,400 B PSRAM。新游戏继续走现有显示驱动，不再叠加全屏Canvas、WebGL、位图解码画布或上游显示驱动。

面板总线在`hardware/scripts/panel_build_flags.ps1:1`为40MHz；仅传输153,600 B整屏数据的理论下限已达30.72ms，还没有计入命令、渲染、拷贝和触摸读取。设计目标应为输入及时、运动稳定与局部重绘，不能承诺60FPS。动作规则可20ms定步，绘制采用现有刷新节奏；水果与跑酷用一个绘图对象和固定实体数组，按旧/新包围盒失效。统计中`display.cpp:160`每次flush都递增计数，因此现有`framesPerSecond()`是flush次数，不等于完整游戏帧率；正式验收需另记录游戏绘制/模拟帧间隔及最大输入延迟。

下列是实现预算上限建议，属于设计约束，尚非新固件测量结果：

| 项目 | 建议预算 | 如何控制／核实 |
|---|---:|---|
| 游戏规则与临时数组 | 当前活动游戏≤16KiB RAM | 跑酷固定障碍/金币池；果切≤12个活动实体、≤24个效果、≤16段短尾迹；不按帧new/delete。实际结构布局在ESP32编译后sizeof记录。 |
| 四款保留状态总量 | ≤32KiB RAM | 非活动游戏不保留LVGL对象；拼块撤销用紧凑移动记录，设上限；密码仅12×4数字与反馈。 |
| 拼块提示 | ≤8KiB辅助空间，UI线程单次≤5ms预算 | 优先有限关卡及已验证解；玩家偏离时可沿撤销路径回到已知可解状态，并明确提示的下一步。若采用搜索，必须分片、有节点/内存上限，不能直接搬无限BFS到设备。 |
| 位图美术 | 本轮0 B大封面/整屏场景 | 猫、地形、果子、拼块和图标采用原生几何绘制；后续如替换小精灵须按最终bin重新核算。 |
| 字体 | 复用已链接字体；新增子集建议≤32KiB Flash | 正文12/14px、标题16px。现有arcade子集仅旧404字符，新名称和说明可能缺字，必须重新提取或使用已完整覆盖的字体，并在真实LVGL检查缺字与裁切。 |
| 常量关卡 | 首版≤8KiB Flash | 使用少量可解关卡/种子与验证解；不再用大量重复地图填满分区。生成关卡必须携带可重放解或完成可解性验证。 |
| 新游戏代码与小资源 | 暂定≤512KiB Flash | 只移植纯规则，渲染/触控/音频调用本工程已有接口；此值为工程预算而非预测，最终以bin与map审核。 |
| 新存档 | 双槽记录每槽≤1KiB | 一局结束、关卡完成、离开时保存分数/关卡/音效设置；不每帧写NVS。是否跨重启恢复棋局以最终设计约定为准。 |

这约1.90MiB是已有常量的回收依据；正式删除引用、链接垃圾回收和新增内容后，新bin减少量仍需重新构建确认。旧规则与UI代码也会回收，但此处不把源码文件字节算成Flash。旧三套8/10/12px arcade字体另分配68,344 B常量、24 B静态缓存；是否回收取决于新方案最终引用，不在上述合计中重复计算。机器可读证据见同目录`resource-reference.json`。

## 存档、音频与上游复用

旧成绩在`arcade_page.cpp:46`的`arcade/best0,best1`中按15项位置保存；推箱子还用`arcade/soklevel`（`arcade_logic.cpp:19`），数独使用`arc_sudoku`（`arcade_puzzles.cpp:27`），俄罗斯方块为`tetris/best`（`tetris_page.cpp:202`）。新游戏使用独立`games_v2`命名空间和显式schema版本；保持旧NVS键不被新四款误读，不格式化整片NVS，不动闹钟、Wi-Fi和触摸校准。

新存档采用双槽、序号、CRC和写入后校验，保存失败保留上一有效槽。网页预览的RAM状态或浏览器存储不能当作设备NVS已实现的证据。

上游跑酷/拼块来自`lepczynski-cloud/crowpanel-pocket-arcade`，果切来自`nikoloskistefan-cell/ESP32-CYD-Fruit-Ninja`，密码参考`VaAndCob/ESP32-S3-Mastermind`；本轮已核实MIT许可。复用规则代码时保留具体来源和版权文本；上游TFT_eSPI、Adafruit显示初始化、XPT2046触摸、引脚及蜂鸣器函数不迁入本机。原版密码的800×480布局也不能直接缩小贴图。

`src/audio_board.h:16`规定预览1、番茄/倒计时2、闹钟3的音频优先级。`knock()`已有异步短反馈且不会抢占提醒（`audio_board.cpp:160`）；`streamPcm()`会等待音频锁，禁止从游戏UI定时器循环推送音乐或调用上游阻塞式蜂鸣器delay。首版可用已有短反馈，开关置于菜单；不显示尚未接入真实音频后端的多种音效选项。若后续增加独立游戏音色，需通过同一异步任务低优先级排队并验证提醒可抢占。

## 确认后可执行顺序与验收

1. 固定本目录设计坐标、命名、规则、胜负和存档范围；保留本轮原生LVGL画面与可操作网页作为对照。
2. 新增纯C++11规则模块和独立四款页面；把网页规则测试案例移植到设备规则测试，避免两套规则悄然分叉。先完成最小一关、准备/暂停/结算/重开，再扩展关卡。
3. 用现有GiftUI入口替换旧16款，删除旧页面调用和资源引用，维持App数值兼容。新游戏厅保持一个定时器、一个活动输入处理器，退出删除timer并清理对象。
4. 规则测试覆盖跑酷最高速度可避障、果切快速跨越及炸弹/漏果判定、拼块全部关卡解与撤销及有效提示、密码重复颜色反馈及12次上限。帧间隔大跳变、暂停冻结、返回重入、重开取消也必须覆盖。
5. 原生LVGL测试读取真实新生产页面，验证全部可见汉字、控件边界、滚动历史、按下/拖动/松开/拖失、菜单输入隔离；比较确认稿几何。独立进程检验双槽保存与损坏回退。
6. 编译完整ESP32镜像，以实际bin和map确认分区余量、无旧游戏常量和状态误读、RAM余量、源码与构建副本一致；运行导航、提醒、音频和触摸原有回归。
7. 进入用户确认过的后续部署流程后，再做实物触摸、连续果切、跑酷响应、提醒抢占、音量与重启存档验收；未实测前不写“已适配通过”。
